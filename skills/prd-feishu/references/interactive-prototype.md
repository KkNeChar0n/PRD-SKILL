# 交互原型工作流

仅在 `prd-feishu` 首次生成或完整重写 PRD 时使用。本文件补充 `SKILL.md` 的原型审查关口。

## 输入与还原

- 用户给的截图、录屏、标注和文字是页面样式与行为的首要依据。截图只显示某个状态，不代表隐藏菜单、按钮后续动作或错误处理已经确定。
- 能访问线上页面时，可读取当前版本作为布局和既有交互参考；把现状和本次新增行为分清。用户的要求优先于现状。
- 未确定但会改变交互路径的事项，用少量具体问题集中向用户确认；不因资料缺口擅自添加支付、删除、审批、权限或其他高影响功能。
- 原型使用模拟数据与本地状态，不调用真实业务 API。必要时明确“模拟提交成功/失败”，让用户看得到状态变化，不暗示后端已实现。

## 单文件原型最低验收

`prototype.html` 必须能独立打开，CSS 与 JS 尽量内联，避免临时文件路径或未固定版本的 CDN。审查前按该需求实际范围逐步点测：

1. 从用户指定入口进入页面，导航、Tab、层级关系与参考一致。
2. 列表、详情、表单或画布之间可到达并返回；操作对象、选中态和编辑态一致。
3. 本次需求涉及的按钮、下拉、筛选、拖拽、弹窗、确认和取消均有可见行为；无“看起来能点但没有反应”的控件。
4. 必填、格式、冲突等关键校验可触发，提示位置和恢复方式明确。
5. 提交成功、失败、等待、空数据等本次需求涉及的状态有可见反馈；页面刷新或重入时，模拟状态处理有清晰约定。
6. 页面在用户要求的尺寸下不裁切关键字段和操作；长列表、弹窗、画布可滚动。

向用户交付 HTML 文件链接和 3～8 步的点击检查路径，等待用户明确通过。记录通过的文件路径与 SHA-256；后续改动若影响界面或交互，要让用户复核新版本。

## PRD 截图与版本共用原型交付

1. 固定用户审查通过的 `prototype.html`，记录 SHA-256。将截图存在同目录的 `screenshots/` 中；截图前实际操作至目标状态，记录状态名称和点击路径。
2. 为每个有“原型图”标题的功能小节选择对应截图。优先覆盖入口、选中或填写后的主要界面、关键弹窗、结果或错误态；同一截图能清楚说明的内容无需重复截。长页面分段截，保持文字和表格可读、没有大块空白或缺失行列。
3. 在 PRD HTML 的对应小节放 `figure[data-prd-screenshot][data-prototype-state][data-prototype-sha256]`，其中 `img src` 与 `data-prd-screenshot` 指向同一 PNG。截图路径相对 PRD HTML 所在目录；发布器按正文顺序把 PNG 放到飞书文档的同一位置。
4. 发布前用 `publish.py <PRD_HTML> <飞书URL> --prototype-attachment <本迭代共用原型.html> --prepare-only` 检查每个“原型图”小节均有截图、路径存在、PNG 可读、原型哈希一致。该命令不写飞书或云效。
5. 正式发布后读回需求 PRD 的正文、图片块和版本文档链接，再读回直接父级版本文档中的 `共用交互原型.html` 文件块，核对附件名称与本次原型版本。需求 PRD 不再存 HTML 副本；飞书文件块本身不运行脚本。

用户明确要求 HTTPS iframe 时，核对托管内容与已审查 HTML 的哈希、嵌入响应头和飞书内实际可用性，再用 `--prototype-html`、`--prototype-url` 模式发布。
